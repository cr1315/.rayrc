# 情報聞き込み（remote-inquiry）

このセッションから届かない環境の「実物」を、ユーザーの PC を中継して読み取ってくるための手順。

## なぜこの形なのか

ネットワークは、ユーザーの PC を中心にしたハブ・アンド・スポークになっていることが多い。

```
                 ┌─────────────────────┐
                 │ ハブ：ユーザーの PC     │  （例：Windows の PowerShell）
                 └────┬───────────┬────┘
              SSH     │           │     SSH
          ┌───────────▼──┐     ┌──▼─────────────────┐
          │ スポーク A：    │  ✕  │ スポーク B：          │
          │ このセッション  │ ─── │ 調べたい環境（踏み台など）│
          └──────────────┘     └────────────────────┘
```

- Claude はスポーク A の中にいて、スポーク B には届かない。
- ハブからは、A にも B にも SSH できる。
- そこで、Claude が A にスクリプトを置き、ユーザーがハブでコマンドの並びを貼るだけで、「A → ハブ → B に送る → B で実行 → B → ハブ → A に戻す」が済むようにする。

往復が 1 回で済むので、推測で進めて後で外れるより、実物を見てから判断するほうが安くつく。

## いつ使うか（使う前に必ず確認する）

使う場面：手元のファイル・記録・推測では確かめられず、届かない環境の実物（動いている設定、クラウドのリソース、ログ、権限）を見れば判断が確定するとき。

使わない場面：このセッションから直接読めるもの（ローカルのファイル、このマシンの CLI で読めるアカウント、Git のリモート）。何でもこれで聞くと、ユーザーの手間を増やすだけになる。

**使う前に、AskUserQuestion のカードで確認する。** 中継するのはユーザーの PC と権限なので、勝手に始めない。カードだけを見て判断できるように、次を書く。

- 何を知りたいか、それで何が決まるか
- 調べる先（スポーク B）のエイリアスと、このセッション（スポーク A）のエイリアス
- スクリプトが読むもの（読み取りだけであること）と、出さないもの（シークレットの値など）
- 結果の置き場所（下の「結果の置き場所」で選んだもの）

選択肢は「この内容で作る」「やめる」を基本にする。エイリアスや置き場所が違うときは、ユーザーが「その他」で直せる。

## 手順

### 1. エイリアスを決める

スクリプトとコマンドの並びで要るのは、ハブから見た SSH のホストのエイリアスの 2 つ（A と B）。

1. 会話・記憶（memory）・過去の記録にあれば、それを使う。
2. なければ、このセッションの `~/.ssh` を探す。SSH の設定を Git で管理し、よく使うホストに同じものを clone しているユーザーもいる。
   - `~/.ssh/config` と、そこから `Include` されているファイルの `Host` / `HostName` / `User` の行だけを読む。
   - **自分（スポーク A）のエイリアス**：`hostname -I` の IP や `hostname` と、`HostName` が一致する `Host` を探す。
   - **調べる先（スポーク B）**：名前（`bastion`、`jump`、環境名など）やコメントから候補を探す。
   - 鍵（`*.pem`、`id_*` など）や、`password`・`secret`・`token` などを名前に含むファイルは開かない。必要なのはエイリアスだけ。
3. 見つからない、または候補が複数あるときは、推測で決めずに確認のカードで聞く。clone はハブの設定より古いことがあり、ハブにしかないエイリアスもある。

### 2. 結果の置き場所を決める

結果には、環境の構成や、ときには人の名前などが入る。誤ってコミットされないよう、**Git の管理外のフォルダ**に戻す。

1. このセッションの作業中のリポジトリで、管理外になっているフォルダを探す。よくあるのは `logs/`・`tmp/`・`temp/`・`build/`・`.cache/` など。

   ```bash
   for d in logs tmp temp build .cache; do [ -d "$d" ] && git check-ignore -q "$d/x" && echo "$d/"; done
   ```

2. 見つかったら、その中に置いてよいかを確認のカードで聞く（候補が複数なら選んでもらう）。`build/` のように、ビルドで消されるフォルダは避けたほうがよいことも書き添える。
3. 見つからないときは、リポジトリの外（例：`/tmp/`）を提案する。リポジトリの中に新しいフォルダを作って `.gitignore` に足す、といった変更は、ユーザーが望んだときだけにする。

### 3. スクリプトを作る（スポーク A の `/tmp` に）

置き場所は `/tmp/<目的>.sh`。リポジトリには置かない。ひな形は `assets/inquiry-template.sh`。
調べる先がクラウド（AWS など）なら、`references/` にその注意点がある（例：`references/aws.md`）。

守ること（理由つき）：

- **読み取りだけ。** describe・list・get・ログの検索まで。作成・変更・削除・再起動はしない。ユーザーの権限で他の環境に触るので、壊しうるものは入れない。
- **実行場所の検査を最初に入れる。** クラウドならアカウント、サーバーならホスト名などを確かめ、違えば何もせずに止める。貼り間違えて別の環境で動いたときの事故を防ぐ。
- **値を出さない。** シークレットは「存在」と「キー名」まで。環境変数などの値は、判断に要るもの（プロファイル名など）だけを許可リストで出す。ログの行は、メールアドレスを伏せ、長さを切る。結果のファイルはハブを通り、ファイルとして残るので。
- **飛ばせるようにする。** 重い章や値に近い章は、`SKIP_KEYS=1`・`SKIP_LOGS=1` のような環境変数で飛ばせるようにする。対象も `ENVS=...` などで絞れるようにする。
- **失敗しても続ける。** `set -u` は使い、`set -e` は使わない。1 つの失敗で全体が止まると、往復をやり直すことになる。エラーは、そのまま結果に出す。
- **向こうにある道具だけを使う。** bash と、そこにある CLI と、`python3 -I` 程度にとどめる。`jq` などは無いかもしれない。B が Windows なら、PowerShell のスクリプトにする。
- **結果は `tee "$OUT"` でファイルに落とす。** ファイル名は、コマンドの並びから `OUT=...` で渡す。
- 作ったら `bash -n` で構文を確かめる。このセッションで動かせる部分（実行場所の検査で止まることなど）は、動かしてみる。

一度に聞けることは一度に聞く。後で「あれも見たかった」となると、往復が 1 回増える。ただし、判断に関係ないものまで集めない。

### 4. ハブで貼るコマンドの並びを作る

ひな形は `assets/snippet-template.ps1`（ハブが Windows の場合）。

**1 行ずつ独立した、平らな並びにする。** 先頭で変数を定義して後の行で使う形にはしない。途中の 1 行が失敗したとき、ユーザーがその行だけを見て、直して、そのまま貼り直せるようにするため。変数を使うと、1 行を直すのに別の行の定義まで追うことになる。

- ファイル名やパスは、すべて行の中に直接書く。日時の付いたファイル名（`<目的>-20250101-120000.txt` のような形）は、Claude がこのセッションで `date +%Y%m%d-%H%M%S` を実行して決め、その値を各行に書き込む。
- ハブの一時置き場は、ハブに元からあるもの（Windows なら `$env:TEMP`）を使う。これはユーザーが定義する変数ではなく、どの PowerShell でもそのまま通る。
- 流れは次の順にする（どの行も単独で貼り直せる）。
  1. A の `/tmp` から、ハブの一時置き場へスクリプトを落とす。
  2. ハブから B へ送る。
  3. B で実行する（`OUT=...` などを付けて）。
  4. 結果を B からハブへ落とす。
  5. ハブから A の置き場所へ送る。
  6. B のスクリプトと結果を消す。ハブの一時ファイルも消す。

**Windows では `ssh` / `scp` ではなく、`ssh.exe` / `scp.exe` と書く。** PowerShell では、`ssh` などを独自の関数やエイリアス（fzf でホストを選ぶものなど）で包んでいることがある。そちらが呼ばれると、対話になったり、コマンドを 1 回で実行できなかったりする。`.exe` まで書けば、それらを通らずに OpenSSH の本体が呼ばれる。ハブが macOS・Linux なら、同じ理由で `command ssh` / `command scp` と書く。

ほかに気をつけること（PowerShell）：

- `"..."` の中の `$名前` は PowerShell が展開する。B のシェルに渡したい `$` は、`` `$ `` と書くか、スクリプトの中に入れる。
- PowerShell 5.1 では、標準出力のリダイレクトでバイナリや UTF-8 が壊れることがある。ファイルの受け渡しは scp で行う。

### 5. ユーザーに渡す

返事には、次をこの順で書く。

1. スクリプトが何を見るか（章ごとに 1 行）と、何の判断に使うか。
2. 出さないもの・飛ばせるもの（`SKIP_*` など）。
3. コマンドの並び（そのまま貼れる形で、コードブロック 1 つに）。
4. 結果が届いたら教えてほしいこと（例：結果のファイルのパスを `@` で添えてもらう）。

### 6. 結果を読む

- 結果のファイルを読み、知りたかったことに答える。手元のファイルとの突き合わせは、目で見比べずにスクリプトで比べる（JSON は正規化して diff するなど）。
- **スクリプトの誤りに気づいたら、そう言う。** 「見つからない」が、実は問い合わせ方の誤りだった、ということがある。その章は信用せず、直したスクリプトで聞き直す。元のスクリプトも直しておく（次回のため）。
- 結果に人の名前やメールアドレスなどが含まれていたら、記録やコミットに書き写さない。ユーザーにも、そのファイルは共有しないよう伝える。
- 聞き直しが要るときは、差分だけを聞く小さいスクリプトにする（全部を流し直さない）。
